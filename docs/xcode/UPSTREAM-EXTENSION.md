# XWork 通用功能迭代：扩展优先、不改上游

XWork 是 ZCode 的下游产品。本文是迭代**通用功能**时的最高指导原则，优先级高于其他实现文档；分支与同步流程仍以 [`BRANCHING.md`](./BRANCHING.md) 为准。

## 1. 适用范围

**通用功能**指上游 ZCode 已经具备、XWork 也在使用的基础能力。例如：登录与认证、Provider 与模型选择、会话与存储、CLI 命令与 TUI、配置加载、插件 / MCP / hooks、i18n、桌面窗口与 Host、远程链路、用量与计费展示、构建与打包。

在这些能力上做 XWork 的定制、接入、修复或增强（例如接入 New API、XWork Zen、品牌、私有后端），都按本文执行。

XWork 独有的全新功能（上游完全没有对应能力）不受第 3 节"必须走扩展"的限制。但它接入上游能力的方式仍要遵守第 4、5 节。

## 2. 目标

- 让 XWork 尽可能直接使用上游能力，随每次同步自然获得上游的修复与改进。
- 让上游同步（`main → sync/upstream-* → release`）尽量不产生冲突；冲突出现时能一眼看出哪部分属于 XWork。
- 不改上游的基础能力：上游行为保持原样，XWork 的差异以可插拔的方式叠加在上面。

## 3. 硬性规则

1. **先复用，后扩展，最后才修改。** 依次确认：
   1. 上游是否已有可直接使用的能力或配置？（例如环境变量、设置项、Provider 注册、插件、命令注册）
   2. 能否通过上游已有的扩展点叠加？
   3. 以上都不行时，才允许最小化修改上游文件（见第 5 节）。
2. **XWork 代码放在新文件、新模块或新包中。** 命名与目录要能一眼看出属于 XWork，例如 `*-xwork.ts`、`new-api-*`、`xcode/` 目录，或已有的 XWork 专属模块。
3. **不改写上游函数的实现。** 不在上游函数里加 `if (isXWork)` 分支，不改上游函数签名，不改上游默认值，不删除上游行为。需要不同行为时，在注册点、工厂或配置层替换或追加实现。
4. **不重新组织上游代码。** 禁止对上游文件做与功能无关的格式化、重命名、移动、拆分或合并。
5. **共享清单只追加。** 修改 i18n 文案、`package.json`、`architecture-policy.yaml`、路由表、注册表这类共享清单时，只追加新条目或使用单独文件；不改动、不删除、不重排已有条目。`pnpm-lock.yaml` 只接受由新增依赖带来的变化。
6. **XWork 的差异集中到配置。** 品牌、域名、服务地址、默认值等差异集中放在配置或资源文件中，不在业务代码里散落替换。
7. **通用 bug 先看上游。** 先确认上游是否已修复（`git log upstream/main --grep=<关键词>`）。上游已修复的，等同步获得；上游未修复、且必须马上修的，按第 5 节最小化修改并登记。

## 4. 推荐的扩展方式

按以下顺序选择：

| 方式                          | 适用场景                                                                    |
| ----------------------------- | --------------------------------------------------------------------------- |
| 环境变量 / 设置项 / 配置文件  | 上游已经暴露的开关、路径、地址                                              |
| 注册表 / 工厂 / Provider 注册 | 新增 Provider、模型来源、命令、工具、登录方式                               |
| 依赖注入 / 服务替换           | 平台差异（Desktop / Web / 本地 / 远程），通过 `IPlatformService` 等现有接口 |
| 插件 / MCP / hooks / skills   | 可独立安装或卸载的能力                                                      |
| 包装（wrapper）/ 组合         | 在上游组件或函数外层加 XWork 行为，不改内部                                 |
| 新增 UI 组件挂到现有插槽      | 在上游已提供的位置追加界面，不改上游组件内部                                |

上游缺少所需扩展点时，优先通过向上游 ZCode 提 PR 增加通用扩展点来解决。在上游接受之前，可以按第 5 节增加一个**最小的、通用的**扩展点（只开放能力，不写 XWork 逻辑），XWork 逻辑本身仍放在独立文件中。

## 5. 不得不修改上游文件时

只在第 3.1 节的前两步都走不通时才允许，并且必须同时满足：

- 改动最小：只加一个调用、一个注册、一个可选参数或一个扩展点，不重写周围代码。
- 在改动处加注释 `// XCODE: <原因>`（非 JS/TS 文件用该语言的注释语法）。
- 在 PR 描述中列出所有被修改的上游文件，并逐个说明为什么不能用扩展方式实现。
- 改动不改变上游原有行为：XWork 关闭相关功能时，上游路径要与原来完全一致。

## 6. 评审与合并检查

所有涉及通用功能的 PR，合并前必须完成以下检查，并在 PR 描述中写明结果：

```bash
# 1. 本 PR 修改（而非新增）了哪些上游文件
git diff --name-only --diff-filter=MDR origin/release...HEAD \
  | while read -r f; do git cat-file -e "origin/main:$f" 2>/dev/null && echo "$f"; done

# 2. 与最新上游预演合并，列出会冲突的文件（exit 0 表示无冲突）
git fetch upstream
git merge-tree --write-tree --name-only HEAD upstream/main
```

- 第 1 项输出的每个文件，都要能在 PR 描述中找到第 5 节要求的理由，且改动处有 `// XCODE:` 注释；做不到的退回改成扩展方式。
- 第 2 项有冲突时，说明冲突来源；本 PR 新引入的冲突要先消除再合并。
- 同时执行 `pnpm typecheck`、`pnpm lint`、`pnpm architecture:check --changed` 及相关测试，如实报告结果。

## 7. 测试与验收

- 下游的测试、隔离和验收需求，优先用上游已有能力加流程解决，例如环境变量、事前备份、事后比对、限制操作范围；不为测试便利而修改上游基础能力。桌面隔离验收按 [`new-api-integration-runbook.md`](./new-api-integration-runbook.md) 的完整隔离检查清单执行。
- XWork 扩展代码的测试放在 XWork 自己的测试文件中，不改上游已有测试；上游测试因 XWork 扩展而失败时，先修扩展，而不是改上游测试的断言。
